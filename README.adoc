== Overview

This repository contains FastText word embedding models that have been converted
from the original `.vec` format to ONNX format for efficient deployment and
inference.

These models provide semantic word embeddings for use in spell checking and
natural language processing applications.

=== Purpose

The FastText ONNX models serve as a semantic similarity backend for the Kotoshu
spell checker. They enable:

* Semantic word similarity calculations
* Context-aware spelling suggestions
* Cross-language semantic comparisons
* Efficient inference via ONNX Runtime

=== Features

* **Multi-language Support**: Models for 54 languages (ar, bg, br, ca, cs, cy, da, de, el, en, eo, es, et, eu, fa, fr, fy, ga, gd, gl, he, hr, hu, hy, ia, id, is, it, ja, ka, ko, la, lb, lt, lv, mk, mn, ne, nl, nn, oc, pl, pt, ro, ru, sk, sl, sr, sv, tk, tr, uk, vi, zh), each in three tiers (mini, fluency, full)
* **Optimized Format**: 37x compression from original FastText vectors for the full tier
* **ONNX Compatible**: Works with onnxruntime 1.23.2+
* **High Quality**: 300-dimensional embeddings in every tier; vocabulary 10K mini, 50K fluency (60K for de), 100K full
* **Easy Integration**: Drop-in compatibility with Kotoshu spell checker

== Coverage status and backlog

The candidate pool is dictionaries-repo languages intersected with the
fastText Common Crawl vectors. After v1.2.0 (55 languages) the pool is
exhausted except for:

* `nb` (Norwegian Bokmal) - fastText publishes `cc.no` but no `cc.nb`;
  converting `cc.no` as `nb` is blocked on the `no`->nb/nn alias decision,
  which is an owner decision (proposal delivered with plan 83, not
  implemented).
* `fi` (Finnish) - no license-clear hunspell source exists upstream;
  dropped at the license hard gate. LibreOffice ships no fi dictionary and
  the only maintained best-effort one carries no license at all. Sourcing
  one upstream is the prerequisite (see kotoshu/dictionaries).
* `nds` (Low German) - ISO 639-2 only; the registry language contract is two-letter codes, so shipping it needs a Resource Spec decision by the owner. It was converted and passed both gates but ships nothing this release.
* `fo` (Faroese), `rw` (Kinyarwanda), `ie` (Interlingue), `fur`
  (Friulian), `tlh` (Klingon) - dictionaries exist in the dictionaries
  repo but fastText publishes no CC vectors for them.

Regional dictionary variants (ca-valencia, de-AT/CH, en-*, es-*, hyw, ltg,
pt-BR/PT, sr-Latn, sv-FI, el-polyton, tlh-Latn) resolve to their base
language models.

Sizes above are the `full` (fp32) tier. Every language also ships `fluency`
and `mini` int8 tiers — see the tier table under _Registry and
distribution_ and `registry.json`, the canonical catalog.

=== Compression Ratio

Original FastText `.vec` files: ~4.3 GB per language
ONNX format: 114.44 MB per language (full tier)

Compression: **37x smaller** with full semantic quality preserved.

== Model Specifications

=== Technical Details

* **ONNX IR Version**: 11
* **ONNX Opset Version**: 11
* **Compatibility**: onnxruntime 1.23.2+
* **Input**: `word_index` (int64, shape=[1])
* **Output**: `embedding` (float32, shape=[300])

=== Architecture

The ONNX models use a simple embedding lookup architecture:

1. **Constant Node**: Contains the embedding matrix (vocab_size x 300)
2. **Gather Node**: Retrieves the embedding for a given word index
3. **Squeeze Node**: Removes the batch dimension

.Model Architecture
[source,text]
----
word_index (int64[1]) → Gather → Squeeze → embedding (float32[300])
     ↓
Embeddings Matrix (Constant)
----

== Usage

=== Python with onnxruntime

[source,python]
----
import onnxruntime as ort
import numpy as np

# Load model
sess = ort.InferenceSession('models/en/fasttext.en.onnx')
input_name = sess.get_inputs()[0].name
output_name = sess.get_outputs()[0].name

# Get embedding for word index
word_index = 0  # Replace with actual word index from vocabulary
embedding = sess.run([output_name], {input_name: np.array([word_index], dtype=np.int64)})[0]

print(f"Embedding shape: {embedding.shape}")  # (300,)
print(f"Embedding: {embedding}")
----

== Registry and distribution

`registry.json` at the repo root is the canonical, versioned catalog of every
resource (Resource Spec v1, `kotoshu.resources/v1`): one entry per language per
tier, each with dimensions, vocabulary size, quantization, sha256, size,
license, and download URLs. It is generated by `scripts/build_registry.py` —
never hand-edited — and validated against `schemas/registry.schema.json` by
`scripts/validate_registry.py`. Resource ids (`kotoshu://models/{lang}/{tier}`)
are stable forever; content changes ship as a new release tag.

Every language ships in three tiers. Sizes are design targets; what actually
gates shipping is a measured eval against the `full` tier of the same language
(`top1_agreement`, `rank_corr`), recorded under `eval/reports/` and linked from
the registry via `eval_ref`.

[options="header"]
|===
|Tier|Size|Recipe|Role
|mini|~3 MB|top-10k vocab · full 300 dims · int8|slim/edge/wasm
|fluency|~15 MB|top-50k vocab · full 300 dims · int8|default tier
|full|~120 MB|current fp32 300d file, unchanged|maximum accuracy, opt-in
|===

Size comes out of the vocabulary and the byte width, never the
dimensions: measured evals showed fastText neighbour rankings do not
survive SVD dim reduction (rank_corr 0.87–0.91), while int8 with full
dims is near-lossless on the retained vocabulary (rank_corr 0.9999).
Vocabulary loss is reported by the coverage metric in each eval report.

An `int4` group-128 variant of the full tier (all 100k rows, 300 dims,
~16.2 MB per language vs 120 MB fp32; each row packed into signed
nibbles in three 128-element groups with one fp32 scale per group) has
been built and evaluated as an experiment (plan 68 B1) but is NOT
shipped: `scripts/build_int4.py` produces run-in-onnxruntime artifacts
whose round-trip is exact, yet only `ru` clears the fluency
`top1_agreement` gate (8/9 languages fail at 0.78–0.94 while
`rank_corr` passes everywhere), and the lever retry
(`scripts/int4_retry_sweep.py`) confirmed the rejection: group sizes
64/32 lift the worst language (`ja`) only to 0.84/0.92 and half-away
rounding changes nothing, so int4 cannot clear 0.95 within the 20 MB
budget (and int4-mini misses the mini gate on `de`). Evidence lives in
`eval/reports/int4.{lang}.json` with the cross-language verdicts,
group-scale overhead analysis and recommendation in
`eval/reports/int4.summary.json`, the retry sweep table in
`eval/reports/int4-retry.summary.json`; adopting any such tier — including the
kotoshu-rs `RowFormat` extension its per-group scales would need — is
owner-gated.

Binaries are distributed as GitHub Release assets; the URL contract is locked
for API v1:

....
https://github.com/kotoshu/models-fasttext-onnx/releases/download/{TAG}/{asset}
https://raw.githubusercontent.com/kotoshu/models-fasttext-onnx/{TAG-or-main}/registry.json
....

`{asset}` is the file basename, one-to-one with the repo layout. Tags and
releases are cut manually by the owner — the release workflow
(`.github/workflows/release.yml`) only reacts to a pushed `v*` tag and never
creates one. What lives in git versus on Releases, and the LFS freeze, is
recorded in link:docs/storage-decision.md[docs/storage-decision.md].

=== Browser and wasm (CORS)

Every registry entry also carries `urls.mirror`, the media-host URL of the
same bytes:

....
https://media.githubusercontent.com/media/kotoshu/models-fasttext-onnx/main/models/{lang}/fasttext.{lang}[.{tier}].onnx
....

GitHub release assets send no `Access-Control-Allow-Origin` header, but the
media host (the LFS content host, where every tier binary and tier vocab
lives since plan 92) sends `Access-Control-Allow-Origin: *` — as does
`raw.githubusercontent.com` for the plain-git `registry.json`. A browser can
therefore fetch the whole stack with no proxy:

[source,javascript]
----
import { loadModel, rerank } from "@kotoshu/wasm"; // 0.2.0+

const registry = await (await fetch(
  "https://raw.githubusercontent.com/kotoshu/models-fasttext-onnx/v1.2.1/registry.json"
)).json();
const entry = registry.resources["kotoshu://models/en/mini"];

const modelBytes = new Uint8Array(await (await fetch(entry.urls.mirror)).arrayBuffer());
const vocabBytes = new Uint8Array(await (await fetch(
  entry.urls.mirror.replace(/\.onnx$/, ".vocab.json")
)).arrayBuffer());

const model = loadModel(modelBytes, vocabBytes);  // KotoshuModel
rerank(model, "puppy", "the dog and the cat");    // f32 in [-1, 1]
model.free();
----

For servers and CLIs the mirror stays the fallback, never the default; for
browsers it is the only legal source of binaries.

== Building from Source

If you want to convert the models yourself from FastText `.vec` files:

.Install Dependencies
[source,bash]
----
pip install onnx onnxruntime numpy
----

.Download and Convert
[source,bash]
----
# Download FastText vectors
wget https://dl.fbaipublicfiles.com/fasttext/vectors-crawl/cc.en.300.vec.gz
gunzip cc.en.300.vec.gz

# Convert to ONNX
python3 scripts/fasttext_to_onnx.py cc.en.300.vec models/en/fasttext.en.onnx --vocab-size 100000
----
